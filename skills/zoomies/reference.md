# zoomies command reference

Generated by `zoomies commands` from dev, with the configuration directory at `/etc/zoomies` and the state directory at `/var/lib/zoomies` (the defaults for a root install on Linux) and no other `ZOOMIES_*` variable set, so the file is the same wherever it is generated. Do not edit: `make generate` rewrites it, and a test fails when it differs from the binary.

## Running Zoomies

### zoomies controller

Run the control plane, and an agent alongside it unless told otherwise

```text
Run the control plane: the scheduler, the API, the web UI and the webhook endpoint.

Usage:
  zoomies controller [--config path]

Flags:
  --config                   path to zoomies.yaml (default: /etc/zoomies/zoomies.yaml, and a missing file is not an error)
  --takeover                 start even though another controller holds this database's lease, and take it from them

Examples:
  zoomies controller --config /etc/zoomies/zoomies.yaml
  ZOOMIES_BIND=0.0.0.0:8080 zoomies controller     # no file at all: defaults plus environment
```

### zoomies agent

Run a runner host's agent, or join this host to a controller

```text
Run this host's agent: long-poll a controller for work, start and stop runners, report what happens.

Usage:
  zoomies agent [--config path]

Flags:
  --config                   path to zoomies.yaml (default: /etc/zoomies/zoomies.yaml)
  --controller               the controller to talk to; overrides agent.controller_url
  --join-token               a join token, used only when this host has no credentials yet
  --log-file                 append the log to this file instead of stderr (the Windows service is installed with one, because a service has no stderr anyone can read)

Examples:
  zoomies agent --config /etc/zoomies/zoomies.yaml
  zoomies agent --controller https://zoomies.example.com --join-token zoojoin_...
```

### zoomies gateway

Publish a private provider API, such as a Proxmox cluster at home, to a controller over Tailcat

```text
Publish a private provider API, such as a Proxmox cluster on your home network, to a controller over Tailcat.

Usage:
  zoomies gateway --target <host:port> [--state-dir path] [--quiet]

Flags:
  --log-format=text          log format: text or json
  --quiet                    do not print the address; for a service whose log is not the place for a credential
  --state-dir                where the gateway keeps its identity, which is its address (default: /var/lib/zoomies)
  --target                   the provider's API as this machine reaches it, e.g. 192.168.1.10:8006 (required)

Examples:
  zoomies gateway --target 192.168.1.10:8006
  zoomies gateway --target pve.lan:8006 --state-dir /var/lib/zoomies
```

## Your fleet (these talk to a controller over its API)

### zoomies status

The Overview, in a terminal

```text
The Overview, in a terminal: counts, pools, recent scaling and anything wrong.

Usage:
  zoomies status [--window 1h]

Flags:
  --ca-file                  PEM file holding the controller's certificate
  --insecure                 do not verify the controller's certificate
  --output=table             table, json or yaml
  --scaling=5                how many recent scaling decisions to show
  --timeout=30s              how long to wait for one request
  --token                    an API token (or ZOOMIES_TOKEN)
  --url                      the controller, e.g. https://zoomies.example.com (or ZOOMIES_URL)
  --window=1h                the window the completed/failed counts and queue waits cover

Examples:
  zoomies status
  zoomies status --window 24h
  zoomies status --output json
```

### zoomies pools

What runners to make, and how many

```text
What runners to make, and how many.

Usage:
  zoomies pools <subcommand> [flags]

Subcommands:
  list                               Every pool, with its live counts and utilisation
  get <pool-id>                      One pool in full, including any dangerous settings
  create --name <n> --labels <l>     Create a pool
  edit <pool-id> [flags]             Change the settings you name and nothing else
  delete <pool-id>                   Delete a pool, draining its runners first
  enable <pool-id>                   Let a pool create runners again
  disable <pool-id>                  Stop creating runners; existing ones drain
  prewarm <pool-id>                  Pre-pull the image on every matching host
  export [--file pools.yaml]         Write every pool to a file another instance can import
  import <file> [--dry-run]          Create and change pools to match an export, previewed first

Run "zoomies pools <subcommand> --help" for the flags each one takes.
```

#### zoomies pools create

Create a pool

```text
Create a pool. The server validates exactly as the UI's wizard does.

Usage:
  zoomies pools create --name <name> --labels <labels> --installation <id>

Flags:
  --arch                     amd64 or arm64
  --backend=docker           docker, podman or process
  --ca-file                  PEM file holding the controller's certificate
  --cache                    mount a disposable performance cache (not workflow storage)
  --cache-repository         owner/name for a repository-scoped cache under an organisation installation
  --cache-scope=pool         cache isolation: pool or repository
  --cache-size=0             cache limit in bytes, enforced by eviction; needs an absolute cache-source (0 is unlimited)
  --cache-source             absolute host path or named-volume prefix
  --cpu-burst                elastic CPU: off, observe (measure without moving a quota) or automatic (lend spare host CPU to busy runners); needs automatic sizing on docker or podman
  --cpu-burst-max=0          the most CPU one runner may be lent up to, in cores; 0 is the host's allocatable CPU
  --cpu-burst-size-builds=true with --cpu-burst automatic, start runners with CARGO_BUILD_JOBS, DOTNET_PROCESSOR_COUNT and the JVM's processor count set to the ceiling, so a build has workers for CPU lent after it started
  --cpus=0                   CPU limit per runner; 0 leaves the size to the host, which gives each runner one slot's share of its machine
  --daemon-cpu-share=0       the daemon's share of a slot's CPU, 10 to 90, where it differs from --daemon-share; a build is CPU in the daemon, so this is usually the one to raise
  --daemon-memory-share=0    the daemon's share of a slot's memory, 10 to 90, where it differs from --daemon-share; the runner holds the checkout and any in-memory work folder, so this is often the one to lower
  --daemon-share=0           for a --docker-mode dind pool sized by its host: the percentage of one slot given to the Docker daemon, for CPU and memory alike, 10 to 90; 0 is an even split
  --disk-gb=0                disk limit per runner, in GiB
  --docker-mode=none         none, dind or host-socket (host-socket gives jobs root on the host)
  --docker-wait              override runners.docker_wait for this pool's runners (empty follows the fleet)
  --drain-timeout            override scheduler.drain_timeout for this pool (empty follows the fleet; 0 leaves a drain unbounded)
  --dry-run                  validate the pool and print the verdict without creating anything
  --enabled=true             whether the pool may create runners
  --env                      environment variables for every job in this pool, e.g. HTTP_PROXY=...
  --ephemeral=true           one job per runner; the safe default
  --host-selector            only use hosts that match, e.g. arch=arm64 or os=windows; os and arch need no label
  --idle-timeout=5m          how long an idle runner waits before being drained
  --image                    runner image (default: the variant --os selects, else the controller's github.runner_image)
  --insecure                 do not verify the controller's certificate
  --installation             the GitHub App installation this pool registers runners with
  --labels                   the labels a workflow's runs-on must ask for (repeatable, or comma-separated)
  --max=4                    the most runners this pool may have at once
  --max-runner-lifetime      override scheduler.max_runner_lifetime for this pool (empty follows the fleet; 0 is no limit)
  --memory-burst             elastic memory: off, observe (decide what it would lend and record it, changing nothing) or automatic (raise a live runner's memory limit out of memory the host has not promised to anyone); needs docker or podman
  --memory-burst-max=0       the most memory one runner may hold, in MiB, its own share and what it is lent together; 0 is half as much again as it starts with
  --memory-burst-spill=0     the swap each container may be allowed beyond its memory limit, in MiB, as the last resort once the host has no memory left to lend; 0 allows none
  --memory-mb=0              memory limit per runner, in MiB; 0 leaves the size to the host
  --min=0                    runners to keep even when nothing is queued
  --min-cpus=0               the least CPU a runner of this pool is given, per container (a Docker-in-Docker pair needs it twice over, scaled by the share); 0 follows the fleet's runners.minimum_cpus
  --min-memory-mb=0          the least memory a runner of this pool is given, per container, in MiB; 0 follows runners.minimum_memory_mb
  --name                     the pool's name; it is stored with the zoomies- prefix, e.g. zoomies-4vcpu-ubuntu-2404
  --no-default-labels        register runners without self-hosted, os and arch labels; needs --ephemeral=false
  --os                       the distribution these runners need: ubuntu, debian, fedora or rocky. It picks the runner image and restricts placement to hosts that match
  --os-version               the release, e.g. 24.04
  --output=table             table, json or yaml
  --pids-limit=0             the container's pids cgroup limit (0 is no limit)
  --priority=0               scheduling priority; higher-priority pools receive create slots first
  --provider-selector        only let providers that match rent machines for this pool, e.g. site=garage or kind=proxmox; name and kind need no label; empty means any provider
  --provision-timeout        override scheduler.provision_timeout for this pool, e.g. 30m (empty follows the fleet; 0 never gives up)
  --pull-policy=if-not-present if-not-present, always, or pinned-only
  --run-as-root              run job steps as root inside the runner
  --runner-group             the GitHub runner group to register into
  --runner-version           pin the actions/runner release
  --scale-up-delay           override scheduler.scale_up_delay for this pool (empty follows the fleet; 0 scales the moment a job is queued)
  --size-from-host           take each runner's size from the host it lands on, as that host's runner sizes say (see zoomies hosts edit); a pool does this or states a size, so it cannot be combined with --cpus or --memory-mb
  --timeout=30s              how long to wait for one request
  --tmpfs-auto               let each runner decide where the in-memory folders live: in memory where the runner has room for one to be useful (2 GB for _work, 1 GB for /tmp, 4 GB for the image store), on disk where it has not; --tmpfs-auto=false makes them always in memory
  --tmpfs-docker             keep the Docker-in-Docker sidecar's image store in memory; needs --docker-mode dind; an image bigger than the store does not pull, and it is charged to the sidecar's memory limit
  --tmpfs-docker-size=0      the image store's ceiling in MiB (at least 64); 0 sizes it from the sidecar's memory limit, at most 8192 and half of it
  --tmpfs-tmp                keep /tmp in memory as well; off unless asked for, because some jobs leave gigabytes there
  --tmpfs-tmp-size=0         the /tmp folder's ceiling in MiB (at least 64); 0 sizes it from the memory limit, at most 1024
  --tmpfs-work               keep the runner's _work folder in memory instead of on the host's disk; the folder is charged to the runner's memory limit; needs docker or podman
  --tmpfs-work-size=0        the _work folder's ceiling in MiB (at least 64); 0 sizes it from the memory limit, at most 4096 and half the limit
  --token                    an API token (or ZOOMIES_TOKEN)
  --url                      the controller, e.g. https://zoomies.example.com (or ZOOMIES_URL)

Examples:
  zoomies pools create --name zoomies-4vcpu-ubuntu-2404 --labels zoomies-4vcpu-ubuntu-2404 --installation ins_k3f9qz2m --cpus 4 --os ubuntu --os-version 24.04 --max 8
  zoomies pools create --name zoomies-8vcpu-debian-12-arm64 --labels zoomies-8vcpu-debian-12-arm64 --installation ins_k3f9qz2m --cpus 8 --os debian --os-version 12 --arch arm64 --dry-run
  zoomies pools create --name zoomies-ubuntu-2404 --labels zoomies-ubuntu-2404 --installation ins_k3f9qz2m --size-from-host --max 12
```

```text
  --include-key              copy the encryption key into the backup as well. Convenient and dangerous: the copy then decrypts itself
  --keep=0                   delete all but the newest N backups in --dir; 0 keeps every one
  --no-offsite               keep the copy on this host, whatever backup.remotes says
  --remote                   send the copy to this backup remote only, instead of every one backup.remotes enables

Examples:
  zoomies backup
  zoomies backup --dir /var/backups/zoomies --keep 7
  zoomies backup --include-key
  zoomies backup --remote offsite
```

### zoomies restore

Put a backup's database back, and fence the fleet while you check it

```text
Put a backup's database in place, invalidating the credentials it froze and fencing the fleet.

Usage:
  zoomies restore <backup-directory> [--replace]

Flags:
  --config                   path to zoomies.yaml (default: /etc/zoomies/zoomies.yaml)
  --from-remote              bring the copy back from this backup remote first; the argument is then a backup id, or `latest`, and naming no backup lists what the remote holds
  --passphrase               deprecated: use --passphrase-file; a flag's value is in the shell history and the process list
  --passphrase-file          a file holding the passphrase that copy was sealed with, when it is not the one in backup.remotes
  --replace                  overwrite the database already at database.path, keeping a copy of it first
  --reset-agent-tokens       forget every host's agent credential, so each agent joins again
  --revoke-api-tokens        revoke every API token as well; they are valid credentials the backup froze

Examples:
  zoomies restore /var/backups/zoomies/zoomies-20260908-181718
  zoomies restore /var/backups/zoomies/zoomies-20260908-181718 --replace
  zoomies restore --from-remote offsite
  zoomies restore --from-remote offsite latest --replace
  zoomies restore --from-remote offsite latest --passphrase-file ./backup.pass --replace
  zoomies restore ... --revoke-api-tokens --reset-agent-tokens
```

### zoomies tune

Review, apply or revert explicitly approved host tuning

```text
Review and apply host tuning with recorded reversals. Defaults to safe changes with per-item confirmation.

Usage:
  zoomies tune [flags]

Flags:
  --background               with --force: do not wait here; start a background task that keeps this host in service and keeps trying until a moment with no containers running, then restarts Docker (it gives up after --give-up-after, and never stops a job)
  --config                   local Zoomies configuration file
  --dedicated                include dedicated-host checks; requires typed confirmation or --yes
  --docker-host              Docker socket on this host
  --dry-run                  print exact file changes and commands without writing anything
  --force                    maintenance restart: where a change needs Docker restarted, stop this host's Zoomies services, wait for running jobs to finish (--wait), restart Docker, and start the services again. Never overrides dependency or managed-configuration guards
  --give-up-after=24h0m0s    with --background or --restart-pending, how long to keep looking for a quiet moment
  --kill-running             with --force, stop containers still running when --wait is over and restart Docker anyway, which ends their jobs
  --only                     comma-separated check IDs; optional changes must be selected explicitly
  --restart-pending          do nothing but the Docker restart a previous tune left pending, retrying until the host is quiet; this is what --background runs, and can be run in a terminal multiplexer on a host without systemd
  --revert                   restore recorded previous values and files
  --skip                     comma-separated check IDs to leave unchanged
  --tier=safe                safe or aggressive
  --wait=10m0s               with --force, how long running jobs are given to finish before the restart is given up
  --work-dir                 host path to runner work directory
  --yes                      explicitly approve selected changes without prompts

Examples:
  sudo zoomies tune
  sudo zoomies tune --dry-run
  sudo zoomies tune --revert
  sudo zoomies tune --dedicated --only service.snapd
```
