# ZF-234: the documentation for ZF-229 to ZF-233 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the documentation package by writing what the earlier packages did not: a *Why a job failed* section, two FAQ entries, every subcommand on the CLI page with a test that holds it there, and the record.

**Architecture:** Three small tasks over Markdown and one test. Most of section 8's list landed with the packages it documents (the Kennel Club page and its generated check list, `connect-claude.md`'s richer `get_job`, the verify column on `problem-codes.md`, `api-surface.md`, and `cli.md`'s `why`, `kennel`, `commands` and the two skill sections), so this plan writes only the gaps the audit found and adds the one test the spec asks for, between the hand-written CLI page and the binary's command list.

**Tech Stack:** Markdown under `docs/` built by mkdocs; one Go test in `internal/docs` using `go run ./cmd/zoomies commands --output json`, as `skill_commands_test.go` already does.

**Spec:** `roadmap/agent-readiness.md` section 8; `ROADMAP.md` ZF-234 and gate row 16 ("`mkdocs build --strict` passes; every new route and command is on its page").

## Global Constraints

- British spelling in prose; no spaced em dash anywhere (`internal/docs/no_em_dash_test.go`); comments say why; commit messages are imperative sentences, no prefix; no model identifiers in anything pushed.
- A docs link that points nowhere fails `python3 -m mkdocs build --strict`; every page edited builds strictly before the push.
- The problem-codes page is the source the catalogue is generated from; this plan does not edit it (its verify column is in place) so `make generate && git diff --exit-code` stays clean.
- Before every push: `make build-nogui`, `make fmt`, `make lint`, `go test ./internal/docs ./cmd/zoomies`, `go mod tidy` leaves `go.mod`/`go.sum` unchanged, `python3 -m mkdocs build --strict`.

## Decisions the spec left open

- **Where "Why a job failed" lives.** A section on `docs/queued-job.md`, numbered 6 after the page's five steps, rather than a sibling page: the page is where a person already is when a job did not run, and the section sends them to `zoomies why`, the job drawer and `get_job`, which each say the same thing. The nav does not change.
- **The two FAQ entries.** "Why did my job fail, and how do I find out?" (the class, the evidence, the catalogue code, the three places that answer) and "Can a coding agent check my workflow files without sending them anywhere?" (`zoomies kennel check`, the `zoomies-kennel` skill, what is not checked offline). Both link onward and stay short, in the FAQ's voice.
- **The skills page.** Section 8 names "the skills page"; `docs/cli.md` carries one section per skill, written by #768 and #773, and the README points at them. Two sections on the page where the command lives are the page; no new page is added.
- **The test between the hand-written page and the binary.** `TestEveryCommandIsDocumented` holds top-level commands; the new `TestEverySubcommandIsDocumented` holds every `zoomies <cmd> <sub>` the binary has to appearing on `docs/cli.md` as `` `zoomies <cmd> <sub>` ``, `` `<cmd> <sub>` `` or `` `<cmd> <sub> ... ` `` (a backticked phrase starting with the two words), which is how the page's tables already name them. The thirteen it finds missing today are documented in this plan, each in the section where its command lives.

## Review Focus

1. A subcommand added to the binary and not to `docs/cli.md` must fail the new test, naming it. Pinned in Task 2.
2. The kennel section names its verbs as `kennel overview` and so on, so the test sees them; a verb named bare (`overview`) must count as undocumented. Pinned in Task 2.
3. Every link the new prose adds resolves under `mkdocs build --strict` (the job drawer's Why section, `zoomies why`, `get_job` on Connect Claude, the kennel skill section). Pinned in Tasks 1 and 3 by the strict build.
4. The FAQ answer about the offline check must say what is not checked on a laptop, so a reader does not take "nothing found" as an all clear. Pinned in Task 1 by a sentence the test asserts.
5. The queued-job section must send a reader to the class before the log, in the spec's words ("reads a verdict before it reads a log"). Pinned in Task 1 by a sentence the test asserts.
