# ZF-235e, Eli: a floating assistant that can read the fleet

Status: the first plan (tool loop, widget, docs) is built, in the pull requests for
Tasks 1 and 2 below. The second plan, subscription providers, is built for Claude Code
only (see "As built" at its end); Codex and Copilot wait for a tool-free mode.

Eli is what the assistant is called from here on. It stands for **Extremely Lively
Intelligence**, which is what the dog it is named after is for a few minutes after
every bath, and what the fleet's name is for. The name appears in the widget, the
chat, the provider-facing system prompt and the docs; "the assistant" stays as the
word for the feature and its settings page.

## What the owner asked for

1. A floating widget, on every page, whenever the assistant is enabled.
2. Access to the Zoomies MCP tools, so Eli can see current runners, jobs, events and
   problems and answer from them, not from a request to paste things in.
3. The name Eli.
4. After that, Claude, ChatGPT and Copilot used through a person's subscription and
   not an API key (the second plan in this file).

Decided with the owner: fleet data is **off for hosted providers until an
administrator opts in**, per provider; the fleet tools are **read-only**; and the
widget and fleet tools come before the subscription providers.

## What exists, and what that settles

* A stateless chat, `POST /api/v1/assistant/chat`, streamed as `delta`, `usage`,
  `done` and `error` frames, for administrators. Today it drops any tool call a
  model makes, and the system prompt says it cannot see the fleet.
* The provider contract already carries tool calls (`assistant.ToolCall`, a `tool`
  message role with a `ToolCallID`). The chat does not use them yet.
* `internal/mcp` already has the fleet's read tools and an in-process API
  (`internal/api/mcp.go`, `inProcessAPI{s, from, as: identity}`) that makes each
  tool call as the caller, through the same router and the same RBAC as a token
  would. Eli reuses it. That is the property to keep: **Eli can never do or see what
  the person using it could not**, because the call is theirs.
* The shell mounts global pieces in `web/src/App.svelte` (`ProblemsDrawer`,
  `CommandPalette`); the widget mounts there.

## Design

### The tool loop (controller)

`Controller.StartAssistantChat` becomes a loop: send the conversation and the tool
definitions; if the model answers with tool calls, run each, append the results as
`tool` messages and ask again; stop when it answers with text, or after **six
rounds** or **twelve calls**, whichever is first, with a sentence saying so.

* **The tool set is a fixed allowlist of read tools**, not "whatever the MCP server
  offers": `fleet_status`, `list_problems`, `list_jobs`, `get_job`, `job_stats`,
  `list_runners`, `list_pools`, `list_hosts`, `host_health`, `label_advice`,
  `get_runner_log`, and the three `kennel_*` tools. The `context_*` tools (a
  repository's source) and every action tool are not offered, and a model that asks
  for one gets the same "not offered" sentence a client would. A test pins the list
  so a new MCP tool is not silently handed to a hosted model.
* **Calls run as the person.** The controller builds the MCP server with
  `Offer` returning false for every action tool, over the in-process API for the
  caller's identity, and calls its tools in process. `internal/mcp` gains an exported
  `Definitions()` and `CallTool(ctx, name, args)` so the loop does not speak
  JSON-RPC to itself.
* **A result is data.** Each is wrapped in a fenced envelope, capped at 16 KiB (the
  tool's own truncation is kept and said), and the system prompt repeats the MCP
  instruction that job, step and branch names, commit text and log output are
  untrusted text anyone with a pull request can write and are never instructions.
  Eli has no write tool, and the page renders answers as text, so an injected
  instruction can at worst mislead; it cannot change the fleet or send data out by a
  link or an image.
* **The system prompt changes** from "you cannot see the fleet" to "you have these
  tools; use them before saying you do not know; say which you used".

### Letting a hosted model see the fleet

* New column on `assistant_providers`: `fleet_access` (boolean, default false), set
  with the provider like its other fields, an `assistant.fleet_access` audit row when
  it changes, and a switch on the provider form: "Let Eli read this fleet through
  this provider". Its help text says what goes out (runner, job, repository, branch
  and workflow names, log excerpts if asked for) and that a local model keeps it on
  the machine.
* When it is off, the tool loop is skipped: Eli answers as today, and says in the
  widget that it cannot see the fleet and where to turn that on.
* Every chat's `done` frame carries the names of the tools called, the widget shows
  them under the answer ("Eli looked at: list_runners, get_job"), and the `assistant.chat`
  audit row records them. Redaction of what a tool returns is the later 7c slice and
  is not in this plan; the opt-in is the control until then, and the docs say so.

### The widget (web)

* A round button with Eli's mark, bottom right of every page, shown when the person
  is an administrator and an enabled default provider exists. On a phone it sits above
  the bottom navigation. It is a real button with an accessible name ("Ask Eli"), a
  tooltip "Eli, Extremely Lively Intelligence", and a shortcut (`e`, listed in the
  shortcut sheet).
* It opens a panel, anchored bottom right on a wide screen and full height on a
  narrow one, holding what `AssistantChat.svelte` holds today, plus a line for the
  tools used and a notice when fleet access is off. The conversation lives in a small
  shared store, so it survives navigating between pages and is gone on reload (stored
  conversations are slice 7e proper).
* Settings, Assistant keeps the provider cards and the test; its inline chat box is
  replaced by a pointer to the widget, so there is one place to talk to Eli.
* Whether to show the widget comes from the providers list the Settings page already
  loads, refreshed when a provider is added, enabled or made the default, so there is
  no new route for it.

## Tasks, each its own pull request

1. **Tool loop, no UI change.** `mcp.Definitions` and `CallTool`, the allowlist and its
   pinning test, the loop with its limits, `fleet_access` (migration, store, API,
   OpenAPI, audit), the new system prompt, `tool` frames, and a fake model that asks
   for a tool. Tests: the allowlist; a hosted provider without `fleet_access` gets no
   tools; the loop stops at its limits; a call is made as the caller (a viewer-scoped
   identity is refused a tool its role lacks); an oversized or hostile result is
   capped and fenced; mutation checks on each rule.
2. **The widget and the name.** Shell mount, shared conversation store, the
   `fleet_access` switch on the provider form, tool names under answers, the shortcut,
   the Settings pointer, docs and a screenshot. Playwright specs, run in CI only (the
   sandbox's Chromium does not match this Playwright).
3. **Docs and record.** `docs/ui.md`, an "Eli" page in the docs, `roadmap/progress.md`,
   `hand-off-ai.md`.

## What this does not do, and what is not verified

* No write tools, no confirmation card, no redaction, no stored conversations, no
  per-person limits: the later slices of `agent-readiness.md` section 9.
* The tool loop depends on the model supporting tool calls. Models that do not will
  answer without them, and Eli will say it could not look. How well any particular
  model (for example the Ollama Cloud one in use now) chooses tools has to be tried
  with a real model; the tests use a fake one.

# The second plan: Claude, ChatGPT and Copilot on a subscription

Approach chosen with the owner: **drive each vendor's own signed-in command line
tool**, so the login stays inside the vendor's tool and Zoomies never holds a
subscription token. It is a provider kind, `cli`, with the tool as a setting
(`claude`, `codex`, `copilot`).

## Constraints that shape it

* **The controller image cannot run these tools.** It is distroless and static, with
  no shell and no Node. The kind works on a host install (the systemd service), where
  the operator installs and signs in to the tool once as the service account. For the
  compose and image deployments it is documented as unavailable, and the provider
  form says why, with a sidecar as a later option.
* **The login is one person's and is shared.** The subscription is whoever signed in
  to the tool on the host; every administrator using Eli spends it. The form says so.
  Per-person subscriptions are out of scope.
* **The vendors' terms are the operator's to read.** Consumer subscriptions are
  generally sold for the vendor's own apps, and automated or shared use may be
  restricted. The form links to each vendor's terms and says this is the operator's
  decision. I have not verified the current terms of any of the three.
* **The tools are agents.** They can run commands and edit files. The adapter runs
  them in an empty temporary directory with the tool's own options that turn tools and
  permissions off, a cleared environment (no `ZOOMIES_*`, no tokens), a timeout, an
  output cap and one call at a time. The exact flags differ by tool and version and
  have to be checked against an installed copy before it is built.
* **Fleet tools do not reach a CLI.** The tool loop above is Zoomies' own, and these
  tools run their own; so a `cli` provider answers without fleet access at first. Giving
  one the MCP tools means pointing it at `/mcp` with a token, which is its own decision.

## Tasks

1. A `cli` provider kind with a fake executable for tests, the sandboxing above, a
   check that runs "Say OK.", and output parsing for the tool's streaming format.
2. One tool at a time (Claude Code first), each against a recorded real transcript.
   I cannot sign in to a subscription in the sandbox, so each needs the owner, or a
   session on a machine with one, to record it.
3. Documentation, including the terms warning and the container limitation.

## As built: Claude Code (the first of the second plan)

Decided with the owner: use the vendor's own command line tool; **only the person who
set the provider up may use it** (Anthropic's terms bar routing other people through
one plan); Claude Code now, Codex and Copilot when they can be run with their tools
off.

What differs from the plan above:

* The kind is `claude_code`, one kind per tool, not a general `cli` kind: each tool's
  flags, output and sign-in check differ, and a general kind would have put a command
  line in the database.
* `assistant_providers.owner_id` (migration 0092) holds who added it. Create sets it,
  update never changes it. Test, update, make-default, list-models and chat refuse
  anyone else with `assistant.provider_not_yours` (403); delete stays allowed so an
  administrator can clear a departed colleague's row. Chat for someone else falls back
  to a provider they may use.
* It is **refused while `assistant.local_only` is on**, and it never offers the fleet
  tools: `fleet_access` is not accepted for the kind, because the tool loop is
  Zoomies' own and Claude Code would be running its own.
* It is run with `-p`, `stream-json`, `--tools ""`, `--strict-mcp-config`,
  `--safe-mode`, `--no-session-persistence` and `--permission-prompts none`, in an empty
  temporary directory, in its own process group, with an environment allowlist, at most
  two at once. Check reads `claude --version` and `claude auth status`, and spends no
  usage; a Claude Code signed in with an API key is refused.
* **Not verified:** nothing has been run against a real `claude`, a subscription or the
  model. The flags are from Anthropic's documentation, read on the day, and the parser
  and the sign-in check are tested against a stand-in program written from the same
  documentation. The first thing to do on a machine with Claude Code installed is
  press **Test** and ask Eli one question.
* **Codex and Copilot** are not built: neither documents a mode with every tool off.
  OpenCode's own tool was considered and left out for the same reason (its JSON output
  is undocumented); OpenCode Zen and Go are API-key presets instead.
